## Product Vision

A hybrid couch co-op dungeon crawler. One shared host screen shows the game world. Each player uses their phone as a lightweight controller. The simulation is always authoritative — clients send input events, never world-state mutations. Local Party Mode is the flagship; the cloud must not sit on the critical gameplay path during local sessions.

**Target outcome:** validate that the input model, co-op loop, and hybrid architecture are fun, stable, and understandable to external playtesters.

## Contracts / Event Protocol

### Session join flow — Phase 1 (GDS-P1, 2026-06-11)
`JoinRequest` and `SessionStateEvent` (with `roomCode`) defined in `packages/shared-types`. Room code generated by simulation server on session start and broadcast to all connected clients. Host displays room code; mobile reads it to join. WebSocket transport over default port 8081.

---

## Simulation / Game Rules

### Session bootstrap — Phase 1 (GDS-P1, 2026-06-11)
Simulation server handles join, room code generation, and player slot broadcast. Session lifecycle: host opens → room code issued → players join by code → slots filled. No game tick running yet — session management only. Authoritative state held in-memory on the simulation server process.

---

## Host Client / Rendering

### Join flow and lobby UI — Phase 1 (GDS-P1, 2026-06-11)
Host client displays room code on lobby screen and updates player slot list in real time as mobile clients join. Built with React + Vite. WebSocket connection to simulation server. No game rendering yet — lobby only.

---

## Mobile Controller

### Join flow UI — Phase 1 (GDS-P1, 2026-06-11)
Mobile controller shows a player join form (enter room code) and transitions to a connected screen on successful join. Built with React + Vite. WebSocket connection to simulation server. No input controls yet — join screen only.

---

## Networking / Transport

### WebSocket baseline — Phase 1 (GDS-P1, 2026-06-11)
All clients connect via WebSocket to `ws://localhost:8081` (local mode). Message framing defined in `packages/net-protocol`. Session events routed through simulation server. No reconnect handling yet. No prediction, reconciliation, or interpolation (Phase 5).

**Known constraints:**
- Local mode only — cloud transport deferred to Phase 5
- No client-side prediction yet
- Dead zone threshold for movement input not yet defined

## Key Design Decisions

These decisions are stable across phases. Agents must not contradict them without an ADR update.

- **Authority never moves to host or mobile.** Simulation server is always authoritative.
- **Clients send input events, not state mutations.** `move`, `cast-start`, etc. — never position or health values.
- **Same simulation core for local and remote.** Transport differs; game rules do not.
- **Mobile UI stays minimal.** Players watch the host screen, not their phones.
- **Cloud is not on the critical path for local sessions.** Local play must work with no internet.
