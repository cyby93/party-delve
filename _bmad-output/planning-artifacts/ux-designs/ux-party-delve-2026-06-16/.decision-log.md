### D-016: Spirit-form phone state
**Decision:** Option A — modified controller. When a player enters spirit form:
- **Left zone:** Movement joystick remains — fully functional. Spirit-form players can still move.
- **Right zone:** 2×2 skill grid remains but 3 cells are locked (greyed, disabled). 1 cell is replaced by a class-specific **spirit-form ability** — different from the player's normal abilities, unique to spirit state.

### D-014: Spirit Bond assignment — host screen
**Decision:** Option B — ambient text overlay. When a bond is assigned:
1. Tether particle line appears in-canvas between the two bonded characters (colored, bond-specific)
2. Brief centered text fades in over the canvas: two player names + bond type (e.g. "Cyby · Dani — Fate Bond") — Uncial Antiqua, subtle spirit-blue glow, no panel or border
3. Text fades out after a few seconds; tether remains for the duration of the run
4. Bond-specific audio plays at assignment moment
Phone-side bond display:

- **Non-bonded players:** Controller stays visible and inactive. A "Continue" button slides in from the top edge — same position, same style as the Interact button. Reuses the established slide-in pattern, no new UI concept needed.
- **Advancing:** Any one player (bonded or non-bonded) tapping "Continue" advances the whole group to the next level. Bonded players tap Continue on their bond card; non-bonded players tap the slide-in Continue button.

### D-008: Phone controller — landscape, 2×2 grid, floating joystick cells

### D-017: Skill-cell joystick gets ring + knob, matching movement
**Decision:** Ability-cell joysticks render the same ring+knob visual language as the movement joystick — a knob that visibly tracks the drag offset inside a ring, not a ring-only aim line. Confirms and formalizes what `mockups/controller-landscape-1.html` already prototyped (`.skill-joystick-outer`/`.skill-joystick-inner`) but the spec text and build never carried through.
**Why:** Consistency — one visual grammar for "this is a joystick" across the whole controller. A ring-only aim line would be a second, unlearned pattern.
**Sizing:** Scaled down from movement's 110px ring / 40px knob to fit the smaller cell — 80px ring / 28px knob, per the existing mockup. Clamps to the cell boundary per the existing cell-boundary rule (EXPERIENCE.md §4, unchanged).

### D-018: AIM_CAST gets a distinct ring/knob treatment from AUTO
**Decision:** AIM_CAST's ring/knob is visually distinct from AUTO's, not a reuse. AUTO's ring/knob stays the current badge color (`accent-spirit`, static/solid). AIM_CAST's ring/knob uses `accent-spirit` **plus a slow pulse** (breathing opacity/scale, ~1.2s cycle) — since `accent-spirit` and `interactive` currently resolve to the identical hex, a token swap alone would be visually a no-op; the pulse is what actually reads as "this is a channel, not a repeating strike." Pulse is drawn from the existing Spirit Chant VFX vocabulary (DESIGN.md D-004: "VFX moments... corruption glows, purification pulse" already establishes pulsing as this layer's idiom for spirit-power-in-progress).
**Correction folded in:** `ABILITY_BADGE_BORDER`/`badgeBorderColor` in `ControllerScreen.tsx` currently color AIM_CAST as `accent-warm` (grouped with RELEASE) — a pre-3.18 leftover from when AIM_CAST was a fire-on-release bridge. Post-3.18, AIM_CAST behaves like AUTO (continuous fire while held), so the badge should move to the `accent-spirit` family too. Flagged for the implementing story, not fixed here (this session owns the spine only).
**Explicitly out of scope:** A channel-progress indicator (visualizing the server's `cast:started`/`cast:cancelled`/channel-refresh state) is a real gap — Story 3.18 added the server events with no mobile-side visual consumer — but it's a HUD/feedback concern separate from the aiming interaction this session covers. Logged as an open item for a future UX pass, not designed here.

### D-019: Ability-cell deadzone — 10px, independent of movement's 8px
**Decision:** Skill-cell joystick deadzone is 10px, a dedicated constant separate from the movement joystick's 8px (`DEADZONE_RADIUS`) and distinct from the ability-cell code's current undocumented 6px.
**Why:** Developer chose an independently-tunable value over sharing movement's constant. 10px sits in the middle of `review-touch-input.md`'s recommended 8–12px band for skill-cell joysticks — a jittery-thumb false-fire during combat (an accidental (0,0)-direction cast) is a worse outcome than movement's false-start, which justifies a slightly larger deadzone than movement's.

### D-020: Continuous-track, per-type commit sampling model
**Decision:** The ring/knob always track the live thumb position for every joystick-driving type (AUTO, RELEASE, AIM_CAST). What differs is *when the fire commits*: AUTO and AIM_CAST fire every tick using the live direction (unchanged from today's 33ms interval); RELEASE fires once, on lift, using whatever direction the knob is at when the thumb lifts (unchanged from today's behavior — this decision formalizes it, doesn't change it). TAP has no ring/knob at all — instant fire on touch-down.
**Why:** This is what the code already does today, just invisibly (RELEASE's `lastDirX/lastDirY` already updates continuously via `onTouchMove`, only the fire call is deferred to `onTouchEnd`). The design task adds the missing visual to make an already-correct model legible, not a behavior change.
